# 分层抽象：什么公共，什么留给项目

这套分层参考 DeepSeek Harness 的实际做法，但不复制它的仓库规则。DeepSeek Harness 的[根 `AGENTS.md`](https://github.com/deepseek-ai/deepseek-harness/blob/master/AGENTS.md) 同时包含全仓命令、长期约束和大量产品特有不变量；[`packages/AGENTS.md`](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/AGENTS.md)、[`docs/AGENTS.md`](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/AGENTS.md)、[skills](https://github.com/deepseek-ai/deepseek-harness/tree/master/.agents/skills)、[Agent Notes](https://github.com/deepseek-ai/deepseek-harness/tree/master/.agents/notes) 和检查脚本再分别承接局部规则、流程、理由和门禁。

可复用的是这种归属关系，不是其中的 Cordis、Session、插件或 TypeScript 规则。

## 六个层次

| 层次 | 回答的问题 | 是否跨项目复用 | 放置位置 |
|---|---|---|---|
| 公共内核 | 代理每次改动都应怎样工作 | 高 | 根 `AGENTS.md` |
| 项目事实 | 这个仓库是什么、怎样运行、哪里危险 | 低 | 根 `AGENTS.md`、架构和开发文档 |
| 能力规则 | 使用某种语言或能力时有哪些不变量 | 中 | 从 profile 选入根或子树 `AGENTS.md` |
| 局部规则 | 某个目录为什么不同 | 低 | 最近的子树 `AGENTS.md` |
| 任务流程 | 做某类任务时按什么步骤判断和验证 | 中到高 | `.agents/skills/` |
| 决策与门禁 | 为什么这样定，以及怎样阻止回归 | 低 | `.agents/notes/` 和可执行检查 |

## 1. 公共内核

公共内核应能原样用于大多数代码仓库，而且只有违反后会明显增加错误风险的规则：

- 先读适用范围内的指令和拥有该行为的文档。
- 保留用户已有改动，不顺手扩大范围。
- 行为变化同步更新拥有它的测试和文档。
- 在外部输入、配置、文件、进程和网络边界校验；失败不能伪装成成功。
- 不提交凭证。
- 按改动面跑最窄的有效检查，只报告实际运行的命令。

公共内核不应假设仓库使用 TypeScript、monorepo、模型调用、插件系统、双语文档或决策记录。

## 2. 项目事实

这些内容不能从别的仓库复制，必须在采用时填写：

- 一句话项目身份和主要用户。
- 架构入口、关键目录和生成文件。
- 安装、测试、类型检查、lint、构建和冒烟命令。
- 当前扩展点、禁止绕过的核心路径和兼容边界。
- 哪些检查由本地负责，哪些由 CI 负责。

占位符不是最终状态。项目没有某项命令或文档时，应删除对应行，而不是留下空壳。

## 3. 能力规则

能力规则只在仓库真的具备该能力时选用。例如：

- TypeScript：静态类型和不可信边界怎样分工。
- Agent 产品：模型可见内容、工具结果和会话记录怎样对应。
- Monorepo：跨包依赖、公共接口和消费者怎样同步。
- 文档集：教程、参考、生成内容和翻译怎样归属。

profile 是候选规则，不是自动追加的正文。选入一条规则前，必须能指出这个项目里的具体对象和验证方式；否则不要选。

## 4. 局部规则

子树 `AGENTS.md` 只写与父级不同的内容。它可以补充更具体的命令、所有权和约束，但不复制公共内核。

判断是否需要子树文件：如果代理进入该目录后，仍可能仅凭根规则做出错误决定，就需要；如果只是路径和模块名不同，不需要。

## 5. 任务流程

skill 适合按需加载的判断过程，例如发布、迁移、文案审查、错误恢复和提交前检查。它不拥有产品当前行为，也不应重复参数表、架构说明或根指令。

一个 skill 的 `description` 只负责说明何时加载；正文负责流程；被检查的事实仍由代码、文档或配置拥有。

## 6. 决策与门禁

决策记录保存会被重新争论的取舍，检查脚本执行可机械判断的不变量。二者都不是公共模板的必选项：小仓库没有持久取舍时可以没有 notes，没有稳定不变量时也不必为了形式新增门禁。

当某条规则满足以下条件时，再把它变成检查：

1. 可以客观判断通过或失败；
2. 违反后会造成实际风险；
3. 检查足够快，误报有明确处理方式；
4. 有一个故意写错的反例证明检查真的会失败。

## 判断一条规则放哪里

依次问：

1. 每次会话都必须看见吗？是则进入根或子树 `AGENTS.md`。
2. 只在某类项目能力存在时成立吗？是则先放 profile，再由项目选入。
3. 它是在描述当前事实吗？是则进入代码、README 或架构文档。
4. 它是在描述一次任务的步骤吗？是则进入 skill。
5. 它是在解释取舍吗？是则进入决策记录。
6. 它能机械判断吗？是则增加检查，而不是再加一句强调。

同一事实可以在使用点保留必要的短契约，但长解释只保留一个归属位置。
