# 代码审查

目标是发现会改变行为或造成维护风险的问题，不是复述改动，也不是把个人偏好包装成缺陷。

## 确定审查范围

- 确认基线和目标版本；无法确认时明确采用的比较范围。
- 读取改动路径适用的指令，以及拥有相关行为的代码、测试和文档。
- 检查完整改动和必要的上下文，不只看最大的文件或 diff 片段。
- 保留审查与修复的权限边界：审查默认不改文件、不提交、不操作 PR。

## 判断问题

优先寻找：

- 正确性、数据丢失、安全、权限和兼容性问题；
- 失败、取消、重试、并发和部分提交后的未知状态；
- 公共接口变化后遗漏的消费者；
- 实现与文档、配置、快照或生成内容不一致；
- 测试没有覆盖的新增分支、边界和失败路径。

一条发现必须说明触发条件、实际后果和具体位置。只有存在可复现或可推导的影响时才报告；纯风格建议和脱离改动范围的旧问题分开说明，不能混入缺陷列表。

## 校验证据

能用聚焦测试、类型检查或静态检查验证时，运行最窄的有效命令。命令通过不能代替语义审查；未运行的检查不能写成通过。

如果发现依赖外部状态、平台或难以复现的时序，写清已确认的事实、推断和仍缺少的证据。

## 报告

先按严重程度列出可执行发现，再给简短总结和验证情况。每条发现包含：

1. 问题和受影响行为；
2. 触发条件或反例；
3. 最小修复方向；
4. 精确文件和尽可能小的行范围。

没有发现时直接说明，并列出仍未覆盖的风险或未运行的验证；不要为了让报告看起来完整而制造问题。
